## Recursive Language Models - Detailed Notes

## What Problem Does This Paper Solve?

Large language models like GPT-5 have a hard limit on how much text they can process at once, called the context window. Even within that limit, performance gets worse as the input gets longer, a phenomenon the paper calls context rot. If you give a model a very long document, it starts forgetting details from earlier parts. This becomes a serious problem when we want LLMs to handle real-world tasks like analyzing an entire codebase, reading thousands of documents, or reasoning over very long chains of thought. The paper asks whether we can scale the effective context size of general-purpose LLMs by orders of magnitude without changing the underlying model architecture.

## The Core Insight

The key idea is that we should not feed the entire user prompt directly into the neural network. Instead, we should treat the prompt as part of an external environment that the model can interact with programmatically. The model gets a symbolic handle to its input, meaning it can point to parts of the prompt and manipulate them through code, without having to load everything into its limited context window at once. This is similar to how a human would handle a very long book: you do not memorise the entire book in one go. You keep it on your desk, flip to relevant sections, take notes, and piece together an answer.

## How Recursive Language Models Work

An RLM sets up a Read-Eval-Print Loop, which is a programming environment like a Python shell. The user prompt is stored as a variable called context inside this REPL. The model does not see the actual prompt text in its context window. Instead, it only sees metadata about the prompt, such as how long it is and how it is structured. The model then writes Python code to interact with the context variable. It can slice the context into smaller pieces, search for keywords using regular expressions, or call a function called llm_query that sends a specific snippet to a sub-model for detailed analysis. The sub-model is another LLM call that can process that snippet in full. Crucially, the model can also call rlm_query, which spawns an entirely new RLM loop, allowing arbitrary depth of recursion. After each step, the REPL executes the code, and only a small summary of the output, like the first few lines, is shown back to the root model. This forces the root model to rely on variables and sub-calls rather than trying to keep everything in its own head. The loop continues until the model sets a variable called Final, at which point that value is returned as the answer.

## Why This is Different from Existing Approaches

The paper compares RLMs against several existing strategies. Context compaction repeatedly summarizes long content once it exceeds a limit, but this loses fine-grained details that might be important. CodeAct agents can execute code in a loop, but they still load the full user prompt into the model context, inheriting its window limitations. Existing agent frameworks like Claude Code or OpenCode allow sub-agents, but they verbalize sub-calls in natural language rather than producing them programmatically, and they are limited by the model output length. The three critical design choices that set RLMs apart are giving the model a symbolic handle to the prompt so it never has to copy the text into its window, allowing outputs that are longer than the context window by building them up in REPL variables, and enabling symbolic recursion where the model can loop over slices of the prompt and launch thousands of sub-calls programmatically rather than calling sub-agents one by one through natural language.

## Experiments and Benchmarks

The paper evaluates RLMs on five different tasks with varying levels of complexity. S-NIAH is a simple needle-in-a-haystack task where the model must find a specific fact buried in unrelated text. BrowseComp-Plus is a multi-hop question answering task where the model must piece together information from up to a thousand documents. OOLONG requires semantically labelling every entry in a dataset and aggregating those labels, which means the work scales linearly with input length. OOLONG-Pairs is even harder because it requires considering all pairs of entries, meaning the work scales quadratically. CodeQA tests understanding of a large code repository. LongCoT-Mini tests long chains of reasoning where sub-problems depend on each other in complex ways. The paper uses GPT-5 and Qwen3-Coder-480B as base models and compares against compaction, CodeAct with and without BM25 retrieval, OpenCode, and Claude Code.

## The Main Results

RLMs consistently outperform every other method across all tasks. On OOLONG-Pairs, which is the hardest task, base GPT-5 scores essentially zero percent while the RLM version achieves 58 percent. On the LongCoT-Mini reasoning benchmark, the RLM improves over the best reported model by 69.5 percent. The performance gap is largest on tasks that are information-dense, meaning every part of the input matters and you cannot just summarize or retrieve a few relevant pieces. Importantly, RLMs achieve these gains while maintaining comparable or even lower API costs than other methods. The median RLM run is actually cheaper than the median base model run, though the average is higher due to outlier trajectories where the model struggles and makes many wasteful sub-calls.

## Training a Native RLM

The paper also demonstrates that it is possible to train a small model specifically to be a good RLM. They took Qwen3-8B, which is a relatively small open model, and fine-tuned it on only 1000 high-quality RLM trajectories collected from the much larger Qwen3-Coder-480B. The key insight in training is that being an effective sub-call model is similar to being a general-purpose reasoning model. Most of the difficulty lies in learning to operate as the root model, meaning knowing when to probe the context, how to chunk it, and when to launch sub-calls. The leaf sub-calls are just regular LLM requests. The resulting RLM-Qwen3-8B improved by a median of 28 percent across all tasks compared to the base Qwen3-8B, and even approached the quality of vanilla GPT-5 on three of the four tasks. This is significant because it suggests that RLM capability can be taught quickly and generalises beyond the training domain, and it opens the door to treating native RLM training as a new axis of scale for improving language models.

## Observed Behaviour in RLM Trajectories

When the paper analyses how RLMs actually behave, several patterns emerge. Models typically start by probing the context with simple code to understand its structure, then decompose the task into sub-tasks and launch recursive sub-calls. GPT-5 tends to be measured and efficient, using around ten sub-calls per task. Qwen3-Coder is much more liberal and sometimes launches thousands of sub-calls for a single simple task, often repeating work or verifying answers multiple times. The first decomposition attempt is very important for overall success. Even if the model later recovers from a bad initial approach, getting it right early on correlates strongly with correct answers. Syntax errors are a major problem, especially for Qwen3-Coder, and higher recursion depths can actually hurt performance because errors in sub-RLMs cascade back up.

## Limitations and Open Problems

RLMs add complexity on top of existing LLMs, which can lead to unintended side effects like exploding sub-call costs when the model gets stuck in loops. All the experiments use sequential blocking calls, which makes RLMs slow compared to just running the base model. Asynchronous sub-calls could dramatically improve runtime. The paper uses a REPL that is not sandboxed, which could be a safety concern in production. The distinction between a final answer and an intermediate thought is currently handled through special tags like FINAL and FINAL_VAR, which the model sometimes gets wrong, outputting its plan as a final answer. The evaluation focuses on tasks that can be decomposed, so it is unclear how RLMs would perform on tasks that require truly holistic understanding of a prompt where decomposition fundamentally loses meaning. Finally, the training recipe, while promising, is still at a very small scale of 1000 examples and a single 8B parameter model.

## Why This Paper Matters

This paper moves the long-standing problem of limited context windows by showing that you can effectively decouple the model context from the input length through a simple programmatic scaffold. It suggests that the future of long-context processing may not be about making bigger context windows, but about teaching models to interact with external memory through code and recursion. The fact that a small 8B model can be trained to approach GPT-5 quality on these tasks after only 48 H100 hours of training is a striking result. It implies that RLM capability is something that can be learned efficiently and that scales with model size, training data, and compute.



## What was the research trying to make possible?

The research was trying to make it possible for language models to process inputs that are orders of magnitude longer than their native context window without suffering from context rot, while keeping costs reasonable. More broadly, it was trying to establish that the way we feed prompts into models, which is directly loading everything into the neural network, is not the only or best way. By treating the prompt as an external object that the model can symbolically and recursively interact with, the effective context becomes unbounded. This is not just about handling longer documents. It is about enabling entirely new classes of applications where models must routinely process tens or hundreds of millions of tokens, such as analysing entire codebases, reading through years of corporate documents, or maintaining coherent reasoning over very long chains of thought. The paper also tries to show that this capability can be taught to smaller models efficiently, which opens the door to making long-context processing accessible without requiring the most expensive frontier models.

## What assumption does it quietly depend on?

The paper quietly depends on the assumption that long prompts can be decomposed into smaller pieces that can be processed independently and then recombined. This is true for many information retrieval and aggregation tasks, but it is not true for everything. Some problems require genuinely holistic understanding where every token influences every other token and decomposing the input fundamentally loses the relationships between parts. For example, understanding a novel themes might require holding the entire narrative arc simultaneously. The paper also assumes that the model has sufficient coding ability to operate the REPL effectively. Smaller or non-coding models struggle as RLMs because they cannot write correct Python to slice, search, and process their context. Another quiet assumption is that the sub-model calls are reliable enough that errors do not cascade. The paper shows that syntax errors in sub-calls propagate upward with higher recursion depths, and this problem would likely get worse with less capable base models. Finally, the paper assumes that metadata about stdout, like a short prefix and the length, is sufficient information for the root model to decide what to do next. In practice, this works because it forces the model to rely on variables in the REPL, but it also means the root model is operating partially blind and must trust its sub-calls completely.

## What becomes obvious after reading it that was not obvious before?

It becomes obvious that the context window is not a fixed property of a model but is deeply intertwined with task complexity. A model might handle a 100K token input perfectly fine for a simple fact retrieval task but fail catastrophically at 30K tokens on a task that requires aggregating information from every part of the input. This means benchmarks like needle-in-a-haystack, which frontier models now ace at a million tokens, are misleading about real long-context capability. What also becomes obvious is that most existing agent frameworks are doing something similar but with a critical flaw. They keep the prompt in the model context and then try to manage it, which is like trying to hold a heavy box while also trying to reorganise its contents. The RLM approach of putting the box down on a table and examining its contents through code is a much more natural and effective paradigm. Another thing that becomes clear is that recursion is not just a fancy trick but a fundamentally different way of using LLMs that gives them more expressive power, similar to how chain-of-thought reasoning turns a finite-state machine into a Turing machine. When a model can call itself programmatically in loops, it can do semantic work that scales with the square of the input length or more, which is simply impossible for a single forward pass of a transformer.

## Where does the idea break if you push it outside the paper?

If you push RLMs outside the paper, several failure modes emerge. First, the cost could explode unpredictably. The paper shows that the median cost is reasonable, but the tail includes trajectories that are extremely expensive because the model gets stuck in verification loops or launches thousands of unnecessary sub-calls. In a production system serving many users, this variance could be unacceptable. Second, the approach depends on the model being able to write correct code, and if the base model makes syntax errors, those errors compound with recursion. A model that is even slightly worse at coding than Qwen3-Coder might fail entirely. Third, latency is a real problem. Because all sub-calls are sequential in the current implementation, a task that requires many sub-calls could take minutes or hours to complete, which is impractical for interactive use cases. Fourth, the approach assumes the REPL execution is safe, but in practice, letting an LLM execute arbitrary Python code in a loop opens up security risks. A malicious prompt could cause the model to write and execute dangerous code. Fifth, if you try to apply RLMs to tasks where the prompt truly cannot be decomposed, like translating a poem where every word choice depends on every other word, the RLM might fragment the input and lose the very quality that makes the task meaningful. Sixth, the paper only evaluates on tasks that have clear right answers. For open-ended creative tasks where there is no ground truth to verify against, the model might confidently produce wrong answers in its sub-calls without any mechanism to catch the error. Finally, the training recipe works for a small 8B model, but scaling it to frontier models would require generating and filtering massive numbers of RLM trajectories, and it is not clear that the simple distillation approach would continue to work at larger scales.

## What long-running problem did this paper move, even slightly?

The paper moved the problem of LLM context limitations from a hardware and architecture problem to a systems and scaffolding problem. For years, the dominant approach to handling longer contexts was to improve the transformer architecture itself, through techniques like ALiBi, sparse attention, or longer training. This paper shows that even with existing models, you can achieve unbounded effective context through a surprisingly simple scaffold. It moves the needle on the problem of making small models more capable. The fact that RLM-Qwen3-8B approaches GPT-5 on three tasks suggests that the gap between small open models and frontier closed models might be partially bridged not by making small models bigger, but by teaching them better strategies for using their existing capability. The paper also moves the problem of task decomposition. It shows that letting the model decide how to decompose a task, rather than using human-engineered workflows, is both feasible and effective, and that the model learns to do this better when given a REPL environment compared to just thinking in natural language. Finally, it moves the problem of recursive self-improvement. Training an RLM on its own trajectories creates a feedback loop where better decision-making as a root model leads to better outcomes, which leads to better training data, which leads to even better decision-making. The paper shows initial evidence of this, and if this loop can be closed more tightly, it could lead to models that become dramatically more capable at long-context tasks simply by practising them.
